# 코드 쉽게 이해하기 (발표·인수인계용)

> 이 문서는 **초보자 눈높이**로 우리 백엔드 코드가 어떻게 동작하는지 설명합니다.
> 발표 전에 한 번 읽어두면 "이 코드가 뭐 하는 거예요?"라는 질문에 답할 수 있습니다.

---

## 1. 한 줄 요약

동아리 행사를 **신청 → 승인 → 출석 → 피드백 → 대시보드**까지 한 곳에서 관리하는 웹 서비스입니다.
서버는 **스프링부트(Java)**, 화면은 **리액트**, 데이터는 **H2** 라는 가벼운 데이터베이스에 저장합니다.

---

## 2. 폴더 구조 — 각 폴더가 하는 일

```
event/        ← 행사 (만들기/수정/상태변경/조회)
application/  ← 신청 (신청·승인·반려·취소)
attendance/   ← 출석 (출석 코드 발급·출석 체크)
feedback/     ← 피드백 (작성·조회)
dashboard/    ← 대시보드 (숫자 집계)
member/, auth/← 회원·로그인
global/       ← 공통 (응답 형식, 에러 처리, 보안 설정)
```

각 폴더 안은 **항상 같은 4종류**로 나뉩니다.

| 폴더 안 | 역할 | 비유 |
| :--- | :--- | :--- |
| `controller` | 요청을 **받는 곳** (주소 연결, 권한 확인) | 가게 **카운터** |
| `service` | 실제 **규칙을 검사하고 처리**하는 곳 | **주방** |
| `repository` | 데이터베이스와 **대화**하는 곳 | **창고 담당** |
| `domain` | 데이터 모양(엔티티)과 enum | **재료/물건** |
| `dto` | 주고받는 **요청/응답 상자** | **포장 상자** |

---

## 3. 요청 하나가 처리되는 순서 (행사 신청 예시)

화면에서 "신청하기" 버튼을 누르면 이런 순서로 흘러갑니다.

```
1. 화면(React)         →  POST /api/v1/events/1/applications  요청을 보냄
2. ApplicationController →  요청을 받고, 로그인한 사람이 누군지 확인
3. ApplicationService  →  규칙 검사: 모집 중인 행사인가? 이미 신청했나?
4. ApplicationRepository → 신청 정보를 데이터베이스에 저장
5. 다시 위로 올라가     →  ApiResponse 형태로 "신청 완료" 응답
```

> **발표 팁:** 이 5단계를 그대로 말하면 "요청이 Controller → Service → Repository → DB를 거쳐 응답된다"를 설명한 게 됩니다.

## 4. 꼭 알아야 할 5가지 개념 (쉬운 비유)

### ① DTO — 주고받는 상자
엔티티(DB랑 똑같이 생긴 객체)를 화면에 그대로 주면 위험합니다. (내부 구조가 다 노출되고, 서로를 참조하다 무한 반복 에러가 날 수 있어요.)
그래서 **화면에 보낼 것만 담은 상자(DTO)** 를 따로 만들어서 주고받습니다.
- 예: `EventResponse`(행사 정보 보낼 때), `EventCreateRequest`(행사 만들 때 받는 값)

### ② ApiResponse — 응답 포장지
성공이든 실패든 **항상 똑같은 모양**으로 응답합니다. 그래야 화면 쪽에서 다루기 편해요.
```json
{ "status": 200, "message": "성공", "data": { ... } }   // 성공
{ "status": 409, "message": "이미 신청한 행사입니다.", "data": null }  // 실패
```

### ③ 권한 (@PreAuthorize) — 출입증
기능마다 "누가 쓸 수 있는지" 출입증을 정해뒀습니다.
- `@PreAuthorize("hasRole('ADMIN')")` → 관리자만 들어올 수 있는 문
- 권한이 없으면 자동으로 **403(접근 권한 없음)** 으로 막힙니다.

### ④ 예외 처리 — 에러를 한 곳에서
규칙을 어기면 `BusinessException` 이라는 에러를 던집니다. (예: "이미 신청한 행사입니다.")
이 에러들을 **`GlobalExceptionHandler` 한 곳에서 모아 받아서**, 알맞은 상태 코드(400/403/409 등)와 메시지로 바꿔 응답합니다.
- 장점: 에러 처리 코드가 여기저기 흩어지지 않고 한 곳에 모입니다.

### ⑤ 상태(Status) — 신호등
행사와 신청은 **단계(상태)** 가 있고, 그 단계에 따라 할 수 있는 일이 달라집니다.
- 행사: `DRAFT(작성중)` → `OPEN(모집중)` → `CLOSED(마감)` → `COMPLETED(종료)` / `CANCELED(취소)`
- 신청: `PENDING(대기)` → `APPROVED(승인)` / `REJECTED(반려)` / `CANCELED(취소)`
- **모집 중(OPEN)** 일 때만 신청되고, **대기(PENDING)** 일 때만 취소됩니다. 잘못된 변경은 막아요.

## 5. 주요 파일 한 줄 설명

| 파일 | 한 줄 설명 |
| :--- | :--- |
| `EventController` | 행사 관련 주소(URL)를 연결하고 권한을 확인 |
| `EventService` | 행사 만들기/수정/상태변경의 실제 규칙 처리 |
| `EventStatus` | 행사 상태와 "어떤 상태에서 어떤 상태로 바뀔 수 있는지" 규칙 |
| `ApplicationService` | 신청·승인·취소 규칙 (모집중만 신청, 중복 차단 등) |
| `AttendanceService` | 출석 체크 (승인자만, 코드 확인, 중복 방지) |
| `DashboardService` | 행사·신청·출석·피드백 숫자 세기 |
| `ApiResponse` | 모든 응답을 감싸는 공통 형식 |
| `ErrorCode` | 에러 종류와 메시지·상태코드 모음 |
| `GlobalExceptionHandler` | 에러를 한 곳에서 받아 응답으로 변환 |
| `SecurityConfig` | 로그인/권한 보안 설정 |

## 6. 발표 때 받을 만한 질문 & 쉬운 답변

**Q. 왜 DTO를 따로 만들었나요?**
A. 데이터베이스 객체를 화면에 그대로 보내면 내부 구조가 노출되고 무한 참조 에러가 날 수 있어서, 보낼 것만 담은 상자(DTO)를 따로 만들었습니다.

**Q. 권한은 어떻게 막나요?**
A. 각 기능 위에 `@PreAuthorize` 로 역할을 적어두면, 권한이 없는 사람은 자동으로 403으로 막힙니다.

**Q. 잘못된 요청은 어떻게 처리하나요?**
A. 규칙을 어기면 `BusinessException` 을 던지고, `GlobalExceptionHandler` 가 받아서 상황에 맞는 코드와 메시지로 응답합니다.

**Q. 중복 신청은 어떻게 막나요?**
A. 신청 전에 "이미 신청했는지" 확인하고, 데이터베이스에도 (행사+회원) 중복을 막는 제약을 걸어뒀습니다.

**Q. 가장 어려웠던 점은?**
A. 기능을 나눠 만들고 합칠 때 충돌이 났던 점, 그리고 출석 숫자를 세는 기준이 두 군데서 달랐던 점입니다. 기준을 통일해서 해결했습니다.

## 7. 실행 방법

```bash
# 1) 백엔드 (시연용 기본 데이터가 자동 생성됨)

# 2) 프론트엔드 (새 터미널)
cd frontend
npm install
npm run dev              # http://localhost:5173
```
